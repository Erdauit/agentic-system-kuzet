Фаза 5 — чат, Setup Assistant и Ops Agent (MVP) на одной RTX 5070 Ti (16 ГБ)

Прочитай CLAUDE.md; SPEC.md §2, §3.2 (шаг 4), §8 (чат и инструменты), §9 (плейбуки), §9.1
пп. 2–4, §12 (Фаза 5), §14 (готовность MVP); docs/prompts/README.md; docs/TODO.md.

Фаза 4 должна быть пройдена: один компактный VLM, выбранный замером, с приоритетами
арбитр > чат > агенты. Контракт ToolCallAudit уже есть. Если llm не работает — скажи и
остановись.

Особенность 16 ГБ: модель маленькая (4–8B, короткий контекст) и делит карту с hot path и
арбитром. Поэтому чат строится так, чтобы надёжность давал код, а не размер модели.

Сначала покажи план (файлы, интерфейсы, тесты) и жди моего подтверждения.

1. **Сервис agents** — LangGraph, чекпоинты в Postgres. Лицензии langgraph и чекпоинтера проверь
   через `make license-gate`, версии зафиксируй в lock. Чат — граф: вопрос → выбор инструментов
   → вызовы → ответ.

2. **Инструменты из SPEC §8.2.**
   - Типизированные (Pydantic), с уровнями read, propose, act. Права — по роли пользователя,
     каждый вызов пишется в аудит (ToolCallAudit).
   - Инструменты будущих фаз (search_archive — Фаза 6, create_monitoring_task — Фаза 7) модели
     не показываются, пока не реализованы; в capabilities — честное «не развёрнуто».
   - Каждый запрет из §8.2 закреплён тестом.

3. **Под маленькую модель.**
   - **Мало инструментов за раз.** Список зависит от роли; лимит вызовов на вопрос и общий
     таймаут — в конфиге.
   - **Компактные результаты.** Инструмент отдаёт итоги и первые N строк. Полные таблицы,
     графики и клипы UI рисует сам по id результата — модель их не перепечатывает.
   - **«Ни одной цифры без источника» проверяет код.** Каждое число в ответе должно встречаться
     в результатах инструментов этого вопроса (с допуском на форматирование). Не сошлось — один
     повтор. Опять не сошлось — ответ без текста модели: «Вот данные:» и карточки результатов.
   - **Нет данных** — чат так и говорит (тест).
   - **Язык ответа совпадает с языком вопроса** (ru или kk). Качество на казахском замерь
     отдельно на evals. Если оно слабое — покажи мне цифры и варианты, не выдавай за готовое.
   - **Чат ниже арбитра.** Пока очередь арбитра не пуста, чат ждёт, а UI показывает «отвечу
     через ~N с». Чат не может вытеснить арбитра (тест).
   - **Контекст ограничен** длиной из Фазы 4. Историю диалога сжимает или обрезает код.

4. **Действия.** propose создаёт черновик. act выполняется только после карточки
   «Подтвердить / Отменить» в UI и с правами роли. Оператор не может выполнить act (тест).

5. **Отдельные инструменты.** look_at_camera — свежий снапшот и вопрос к VLM с приоритетом чата.
   generate_shift_report — PDF (ReportLab уже в проекте).

6. **Фидбек и комментарии операторов** попадают в контекст только как цитируемые данные, не как
   инструкции. Это проверяет тест на подмену инструкций в комментарии.

7. **Помощники.**
   - Setup Assistant (шаг 4 мастера): по снапшоту описывает сцену, рекомендует сценарии и
     предупреждает о возможных ложных срабатываниях. Только propose.
   - Ops Agent: читает метрики (белый список шаблонов PromQL) и логи, даёт понятные
     рекомендации. Только read и propose.

8. **Плейбуки по §9** для chat, setup_assistant и ops: SYSTEM.md, config.yaml, tools.yaml,
   schema.py, evals/. Команда `qoima eval agents`.
   - В CI нет GPU, поэтому evals там не прогнать. Сделай так: `qoima eval agents` на этой
     машине пишет отчёт с хэшем файлов плейбука. CI падает, если плейбук изменился, а свежего
     пройденного отчёта для этого хэша нет.

9. **30 эталонных вопросов** в src/agents/playbooks/chat/evals/ на детерминированной тестовой
   базе (засеянные инциденты, камеры, смены), чтобы правильный ответ был известен заранее.
   Черновик набора на ru и kk сделай сам — я добавлю реальные вопросы с объекта.

10. **UI.** Раздел «Чат»: таблицы, графики, клипы, карточки подтверждения; подписи на ru и kk.

Приёмка:

- под нагрузкой на арбитр чат ждёт, а арбитр не замедляется;
- остановили llm — чат честно «недоступен», алерты идут;
