## Фаза 0

1. **Имя сценария.** В SPEC.md §0 сценарий падения назван `fall_and_lying`, а файл конфигурации —
   `fall.yaml`. В коде везде используется `fall` (`ScenarioKind.FALL`), `fall_and_lying` = `fall`.
2. **Раскладка uv workspace.** Каждый каталог `src/<сервис>/` — отдельный пакет workspace со своим
   `pyproject.toml`; импортное имя совпадает с именем каталога (`shared`, `core_api`, …), как в
   SPEC.md §11. Сборка — hatchling с префиксом `sources` и `dev-mode-dirs`. Имена `shared`, `cli`,
   `agents` — общие; в каждом образе ставится только свой пакет, поэтому конфликтов нет, но при
   добавлении сторонних пакетов с такими же импортными именами нужно переименование в `qoima_*`.
3. **Драйвер Postgres — asyncpg.** psycopg/psycopg2 распространяются под LGPL, которой нет в белом
   списке SPEC.md §2.7. asyncpg — Apache-2.0.
4. **Пакеты вне белого списка после технического ревью** (`src/shared/licenses/policy.yaml`):
   `certifi` (MPL-2.0), `typing-extensions` (PSF-2.0), `greenlet` (MIT AND PSF-2.0), `pathspec`
   (MPL-2.0, только dev). Все — без copyleft на наш код. **Требуется подтверждение юриста Qoima.**
   Рекомендация: после подтверждения добавить PSF-2.0 в белый список.
5. **MediaMTX `-ffmpeg`.** Используется образ с ffmpeg (Alpine): в нём есть `wget` для
   healthcheck, а ffmpeg понадобится симулятору камер (Фаза 1). ffmpeg — отдельная программа,
   с кодом Qoima не линкуется; лицензия сборки ffmpeg (LGPL/GPL) **требует подтверждения юриста**.
   Альтернатива — «чистый» образ MediaMTX (scratch) и healthcheck силами core-api.
6. **Права на секреты.** SPEC.md §3.1 требует «права 600». Docker Compose без swarm монтирует
   secrets с правами файла на хосте, а процессы контейнеров работают под своими uid (postgres — 999,
   сервисы Qoima — 10001), поэтому файлы 600 им недоступны. Решение: каталог `.secrets/` — 700
   (никто, кроме root, не может в него зайти), файлы внутри — 644. `qoima doctor` проверяет права
   каталога.
7. **LLM-сервис не развёрнут.** SPEC.md §4 требует выбрать vLLM или SGLang по бенчмарку — это
   Фаза 3/4. До этого `llm` в compose нет, health показывает «не развёрнуто», а система работает в
   штатном режиме без VLM-арбитража (fail-open, SPEC.md §4.1).
8. **Triton** запускается в GPU-профилях с пустым репозиторием моделей
   (`--model-control-mode=explicit`); модели загружает Deployer (Фаза 7).
9. **Образы vision-pipeline и worker-gpu** в Фазе 0 построены на `python:slim`: CUDA/TensorRT/PyAV
   появятся вместе с кодом, который их использует (Фазы 2 и 7), после бенчмарка. Видимость GPU в
   контейнере уже проверяется (`nvidia-smi` пробрасывает nvidia-container-toolkit).
10. **Офлайн-установка.** Подписанные офлайн-бандлы — Фаза 9. `install.sh --bundle` честно
    отказывает; сейчас установка требует доступа в интернет (PyPI, npm, Docker Hub, ghcr.io, nvcr.io).
11. **node-exporter** работает во внутренней сети compose, а не в `network_mode: host`, чтобы не
    открывать порт на хосте. Метрики CPU/памяти/дисков хоста корректны (`/host`), сетевые — уровня
    контейнера.
12. **Минимальная версия драйвера.** Образ Triton 26.08 собран на CUDA 13.4 → драйвер должен
    поддерживать CUDA 13.x (R580+). `qoima doctor` сравнивает версию CUDA из шапки `nvidia-smi` с
    `doctor.min_driver_cuda_version: "13.0"`.
13. **Стартовые пороги** с пометкой «уточняется» в `configs/defaults.yaml` и `configs/scenarios/`
    (яркость чёрного/пересвеченного кадра, доля заслонения, сдвиг ракурса, серые зоны T_low/T_high,
    окна дедупликации и cooldown) — инженерные значения по умолчанию. Они калибруются на камерах
    объекта в Фазах 1–3 и пересчитываются Trainer/Evaluator.
14. **Health «Время».** Контейнер core-api не видит состояние chrony хоста, поэтому в UI статус
    «нет данных» с подсказкой; синхронизацию проверяет `qoima doctor` (до Фазы 1).
15. **Раздел UI.** В Фазе 0 работает только «Состояние системы»; остальные разделы видны в меню
    с номером фазы, в которой появятся. Переводы на казахский язык нуждаются в вычитке носителем.
16. **Шаблоны URL камер** (`configs/camera_url_templates.yaml`) взяты из документации
    производителей и помечены `verified: false` до проверки на реальных камерах.
17. **Проверено локально без GPU.** Фаза 0 проверена на macOS (Docker Desktop, профиль `--no-gpu`):
    тесты, сборка образов, `qoima up`/`status`/`doctor`. GPU-профили (Triton, DCGM, резервирование
    GPU) проверены только `docker compose config` — приёмку на сервере с GPU нужно провести на
    целевом железе.

## Фаза 1

18. **FFmpeg собирается свой (LGPL).** Колёса PyAV с PyPI заявляют лицензию LGPL, но содержат
    `libx264` и `libx265` (GPL). Образ `media-base` собирает FFmpeg 9.0.2 без GPL-компонентов,
    PyAV в образах собирается из исходников (`--no-binary-package av`); сборка падает, если PyAV
    окажется связан не с этой сборкой. На машине разработчика (`uv sync`) используются колёса
    PyPI — они не распространяются. GPL-фильтр `boxblur` в нашей сборке недоступен — симулятор
    использует `gblur`.
19. **Нативные библиотеки в колёсах** (OpenCV-headless: FFmpeg LGPL, OpenSSL 1.1.1, libgfortran
    с GCC runtime exception, OpenBLAS) перечислены в `src/shared/licenses/components.yaml: native`.
    Гейт видит только метаданные пакетов — **нужно подтверждение юриста** и плановое обновление
    OpenSSL (1.1.1 снят с поддержки).
20. **Автопоиск из контейнера.** Multicast WS-Discovery не проходит через NAT Docker, поэтому
    основной способ — адресные (unicast) WS-Discovery-запросы и TCP-сканирование портов RTSP/ONVIF
    по подсетям сервера (их передаёт `qoima up`) и из `discovery.subnets`. Сеть backend не
    сканируется (нет маршрута наружу). Поиск — только по кнопке администратора.
21. **ONVIF-клиент свой** (5 вызовов Profile S, WS-Security PasswordDigest с поправкой на часы
    камеры), без onvif-zeep. XML с DOCTYPE/ENTITY отвергается.
22. **Camera Health декодирует только I-кадры** (CPU, PyAV) — достаточно для всех проверок §5.9
    и дёшево. «Замёрз» — средняя разница миниатюр 160×90 ≤ 0.2 (замер: норма 3–7, заморозка 0.0);
    dHash не годится — он не отличает статичную сцену от замёрзшей. Сдвиг ракурса — смещение по
    ORB+RANSAC при ≥ 12 совпадениях, иначе «сцена не узнана». Пороги уточняются на объекте.
23. **Настройки из мастера** пишутся в `${DATA_ROOT}/config/site.yaml` (проверка QoimaConfig,
    атомарная запись, аудит). `configs/` — значения поставки, только чтение.
24. **Пароли камер и токен бота** — `.secrets/runtime/` (каталог 700, файлы 600, владелец — uid
    core-api 10001). В API и логах не появляются; vision-pipeline их не знает (читает MediaMTX).
25. **Вход.** Пароли — scrypt (stdlib), серверные сессии (в БД — sha256 токена), cookie
    HttpOnly/Secure/SameSite=Strict, CSRF — обязательный заголовок `x-qoima-request`. Первый вход —
    `admin` с паролем из `.secrets/admin_initial_password`, смена обязательна.
26. **Шаг 2 мастера и «Время»** — по отчёту `qoima doctor --report` (systemd-таймер раз в 5 мин):
    из контейнера не видно драйвер, chrony и диски хоста.
27. **Каналы алертов в Фазе 1** — web, Telegram, HTTP-реле: тестовая отправка и доставка
    системных алертов. Маршрутизация инцидентов, эскалация, Modbus — Фаза 2.
28. **/metrics core-api** перенесён на внутренний порт 9464 (не публикуется), чтобы метрики не
    были видны в сети завода через порт UI.
29. **Симулятор камер** (`qoima sim`) — отдельный образ на `media-base` + ONVIF-сервер (stdlib),
    логин/пароль `admin` / `qoima-sim`. Только для разработки и e2e.
