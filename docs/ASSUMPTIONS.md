## Фаза 0

1. **Имя сценария.** В SPEC.md §0 сценарий падения назван `fall_and_lying`, а файл конфигурации —
   `fall.yaml`. В коде везде используется `fall` (`ScenarioKind.FALL`), `fall_and_lying` = `fall`.
2. **Раскладка uv workspace.** Каждый каталог `src/<сервис>/` — отдельный пакет workspace со своим
   `pyproject.toml`; импортное имя совпадает с именем каталога (`shared`, `core_api`, …), как в
   SPEC.md §11. Сборка — hatchling с префиксом `sources` и `dev-mode-dirs`. Имена `shared`, `cli`,
   `agents` — общие; в каждом образе ставится только свой пакет, поэтому конфликтов нет, но при
   добавлении сторонних пакетов с такими же импортными именами нужно переименование в `qoima_*`.
3. **Драйвер Postgres — asyncpg.** psycopg/psycopg2 распространяются под LGPL, которой нет в белом
   списке SPEC.md §2.7. asyncpg — Apache-2.0.
4. **Пакеты вне белого списка после технического ревью** (`src/shared/licenses/policy.yaml`):
   `certifi` (MPL-2.0), `typing-extensions` (PSF-2.0), `greenlet` (MIT AND PSF-2.0), `pathspec`
   (MPL-2.0, только dev). Все — без copyleft на наш код. **Требуется подтверждение юриста Qoima.**
   Рекомендация: после подтверждения добавить PSF-2.0 в белый список.
5. **MediaMTX `-ffmpeg`.** Используется образ с ffmpeg (Alpine): в нём есть `wget` для
   healthcheck, а ffmpeg понадобится симулятору камер (Фаза 1). ffmpeg — отдельная программа,
   с кодом Qoima не линкуется; лицензия сборки ffmpeg (LGPL/GPL) **требует подтверждения юриста**.
   Альтернатива — «чистый» образ MediaMTX (scratch) и healthcheck силами core-api.
6. **Права на секреты.** SPEC.md §3.1 требует «права 600». Docker Compose без swarm монтирует
   secrets с правами файла на хосте, а процессы контейнеров работают под своими uid (postgres — 999,
   сервисы Qoima — 10001), поэтому файлы 600 им недоступны. Решение: каталог `.secrets/` — 700
   (никто, кроме root, не может в него зайти), файлы внутри — 644. `qoima doctor` проверяет права
   каталога.
7. **LLM-сервис не развёрнут.** SPEC.md §4 требует выбрать vLLM или SGLang по бенчмарку — это
   Фаза 3/4. До этого `llm` в compose нет, health показывает «не развёрнуто», а система работает в
   штатном режиме без VLM-арбитража (fail-open, SPEC.md §4.1).
8. **Triton** запускается в GPU-профилях с пустым репозиторием моделей
   (`--model-control-mode=explicit`); модели загружает Deployer (Фаза 7).
9. **Образы vision-pipeline и worker-gpu** в Фазе 0 построены на `python:slim`: CUDA/TensorRT/PyAV
   появятся вместе с кодом, который их использует (Фазы 2 и 7), после бенчмарка. Видимость GPU в
   контейнере уже проверяется (`nvidia-smi` пробрасывает nvidia-container-toolkit).
10. **Офлайн-установка.** Подписанные офлайн-бандлы — Фаза 9. `install.sh --bundle` честно
    отказывает; сейчас установка требует доступа в интернет (PyPI, npm, Docker Hub, ghcr.io, nvcr.io).
11. **node-exporter** работает во внутренней сети compose, а не в `network_mode: host`, чтобы не
    открывать порт на хосте. Метрики CPU/памяти/дисков хоста корректны (`/host`), сетевые — уровня
    контейнера.
12. **Минимальная версия драйвера.** Образ Triton 26.08 собран на CUDA 13.4 → драйвер должен
    поддерживать CUDA 13.x (R580+). `qoima doctor` сравнивает версию CUDA из шапки `nvidia-smi` с
    `doctor.min_driver_cuda_version: "13.0"`.
13. **Стартовые пороги** с пометкой «уточняется» в `configs/defaults.yaml` и `configs/scenarios/`
    (яркость чёрного/пересвеченного кадра, доля заслонения, сдвиг ракурса, серые зоны T_low/T_high,
    окна дедупликации и cooldown) — инженерные значения по умолчанию. Они калибруются на камерах
    объекта в Фазах 1–3 и пересчитываются Trainer/Evaluator.
14. **Health «Время».** Контейнер core-api не видит состояние chrony хоста, поэтому в UI статус
    «нет данных» с подсказкой; синхронизацию проверяет `qoima doctor` (до Фазы 1).
15. **Раздел UI.** В Фазе 0 работает только «Состояние системы»; остальные разделы видны в меню
    с номером фазы, в которой появятся. Переводы на казахский язык нуждаются в вычитке носителем.
16. **Шаблоны URL камер** (`configs/camera_url_templates.yaml`) взяты из документации
    производителей и помечены `verified: false` до проверки на реальных камерах.
17. **Проверено локально без GPU.** Фаза 0 проверена на macOS (Docker Desktop, профиль `--no-gpu`):
    тесты, сборка образов, `qoima up`/`status`/`doctor`. GPU-профили (Triton, DCGM, резервирование
    GPU) проверены только `docker compose config` — приёмку на сервере с GPU нужно провести на
    целевом железе.

## Фаза 1

18. **FFmpeg собирается свой (LGPL).** Колёса PyAV с PyPI заявляют лицензию LGPL, но содержат
    `libx264` и `libx265` (GPL). Образ `media-base` собирает FFmpeg 9.0.2 без GPL-компонентов,
    PyAV в образах собирается из исходников (`--no-binary-package av`); сборка падает, если PyAV
    окажется связан не с этой сборкой. На машине разработчика (`uv sync`) используются колёса
    PyPI — они не распространяются. GPL-фильтр `boxblur` в нашей сборке недоступен — симулятор
    использует `gblur`.
19. **Нативные библиотеки в колёсах** (OpenCV-headless: FFmpeg LGPL, OpenSSL 1.1.1, libgfortran
    с GCC runtime exception, OpenBLAS) перечислены в `src/shared/licenses/components.yaml: native`.
    Гейт видит только метаданные пакетов — **нужно подтверждение юриста** и плановое обновление
    OpenSSL (1.1.1 снят с поддержки).
20. **Автопоиск из контейнера.** Multicast WS-Discovery не проходит через NAT Docker, поэтому
    основной способ — адресные (unicast) WS-Discovery-запросы и TCP-сканирование портов RTSP/ONVIF
    по подсетям сервера (их передаёт `qoima up`) и из `discovery.subnets`. Сеть backend не
    сканируется (нет маршрута наружу). Поиск — только по кнопке администратора.
21. **ONVIF-клиент свой** (5 вызовов Profile S, WS-Security PasswordDigest с поправкой на часы
    камеры), без onvif-zeep. XML с DOCTYPE/ENTITY отвергается.
22. **Camera Health декодирует только I-кадры** (CPU, PyAV) — достаточно для всех проверок §5.9
    и дёшево. «Замёрз» — средняя разница миниатюр 160×90 ≤ 0.2 (замер: норма 3–7, заморозка 0.0);
    dHash не годится — он не отличает статичную сцену от замёрзшей. Сдвиг ракурса — смещение по
    ORB+RANSAC при ≥ 12 совпадениях, иначе «сцена не узнана». Пороги уточняются на объекте.
23. **Настройки из мастера** пишутся в `${DATA_ROOT}/config/site.yaml` (проверка QoimaConfig,
    атомарная запись, аудит). `configs/` — значения поставки, только чтение.
24. **Пароли камер и токен бота** — `.secrets/runtime/` (каталог 700, файлы 600, владелец — uid
    core-api 10001). В API и логах не появляются; vision-pipeline их не знает (читает MediaMTX).
25. **Вход.** Пароли — scrypt (stdlib), серверные сессии (в БД — sha256 токена), cookie
    HttpOnly/Secure/SameSite=Strict, CSRF — обязательный заголовок `x-qoima-request`. Первый вход —
    `admin` с паролем из `.secrets/admin_initial_password`, смена обязательна.
26. **Шаг 2 мастера и «Время»** — по отчёту `qoima doctor --report` (systemd-таймер раз в 5 мин):
    из контейнера не видно драйвер, chrony и диски хоста.
27. **Каналы алертов в Фазе 1** — web, Telegram, HTTP-реле: тестовая отправка и доставка
    системных алертов. Маршрутизация инцидентов, эскалация, Modbus — Фаза 2.
28. **/metrics core-api** перенесён на внутренний порт 9464 (не публикуется), чтобы метрики не
    были видны в сети завода через порт UI.
29. **Симулятор камер** (`qoima sim`) — отдельный образ на `media-base` + ONVIF-сервер (stdlib),
    логин/пароль `admin` / `qoima-sim`. Только для разработки и e2e.

## Фаза 2

30. **Участок (area) зоны** — ключ дедупликации между камерами: события одного типа на одном
    участке → один инцидент; без участка — по камере и зоне. Участок задаётся в редакторе зон
    (мастер, шаг 5) одинаковым у камер, которые видят одно место.
31. **Окно объединения.** Активный инцидент (OPEN/ACKNOWLEDGED) поглощает новые события, пока с
    последнего события ≤ `incidents.dedup_window_s` или с открытия ≤ `incidents.cooldown_s`.
    Закрытый инцидент не поглощает ничего: новое падение после закрытия — новый алерт (fail-open,
    SPEC.md §2.1). Новое событие в принятом инциденте — повторный звук в веб-UI, без Telegram.
32. **Служебные события.** Самотест (мастер, шаг 8) и канарейка просят vision-pipeline создать
    событие на настоящей камере (команда `inject_event` в `qoima:pipeline:commands`): кадр и клип —
    из GOP-буфера, дальше обычный путь. Самотест уходит сразу во все каналы всех уровней с пометкой
    «САМОТЕСТ» и не эскалирует; канарейка — только в системную ленту веб-UI (инженеры), каждые
    `canary.interval_minutes`, провал за `canary.timeout_s` → системный алерт `canary_failed`.
    Канарейка с прогоном ролика через модели — когда будут ролики и веса (docs/TODO.md).
33. **Модели только в ONNX.** Экспорт RF-DETR/RTMPose делает инженер Qoima (`tools/models/`), на
    объекте нет torch. Исполнитель — ONNX Runtime: CPU в разработке/CI, TensorRT EP (FP16, кэш
    движков по GPU/драйверу/версии onnxruntime) на объекте, за одним интерфейсом `OnnxModel`.
    Пред- и постобработка RF-DETR и RTMPose (SimCC) — свои, сверены с исходниками rfdetr 1.11 и
    rtmlib 0.0.16 (без rtmlib в зависимостях).
34. **GOP-буфер** — сжатые пакеты substream и mainstream за `pipeline.gop_buffer_seconds` (лимит
    `gop_max_mb_per_stream` на поток), метки — настенное время (смещение pts фиксируется при
    подключении). Клип — из mainstream без перекодирования (MP4 faststart; SPS/PPS из SDP
    дописываются перед первым ключевым кадром), ключевые кадры декодируются от ближайшего I-кадра.
    Кадр-доказательство пишется сразу при событии (алерт уходит с фото), клип и 4–6 ключевых
    кадров — через `clip_post_s`, отдельным сообщением.
35. **Трекер** сопоставляет детекции с лучшим IoU из предсказания Калмана и последнего наблюдения:
    при резкой остановке (человек упал и лёг) скорость фильтра уносит предсказание, и без этого
    трек рвался вместе с историей падения (найдено тестом).
36. **Доставка.** Строка `alert_deliveries` на (инцидент, канал, получатель, уровень); обработчик
    арендует созревшие строки, отправляет без открытой транзакции, повторяет с паузой 1 → 2 → 4 …
    ≤ `max_backoff_s`. После `max_attempts` — `failed` и системный алерт `alert_delivery_failed`
    инженерам; успешная доставка в этот канал снимает его. Сообщение может прийти дважды (падение
    посреди отправки), но не потеряется. Клип в Telegram — отдельной доставкой вдогонку.
37. **Сирена Modbus/TCP** (pymodbus, BSD-3): катушка включается на `pulse_seconds` или до
    подтверждения инцидента оператором. OPC UA не реализован (docs/TODO.md).
38. **Сообщение из потока, падающее с ошибкой**, повторяется 5 раз, затем откладывается в
    `<поток>:dead` (лог `stream_message_dead_lettered`), чтобы ошибка одного сообщения не
    останавливала все следующие события.
39. **Важность инцидента** по типу: падение и дым/огонь — critical, красная зона — high. VLM
    (Фаза 4) сможет только повысить/обогатить, не подавить (fail-open).
40. **Подтверждение и закрытие.** «Принять» — оператор взял в работу (сирена выключается).
    «Подтвердить: тревога реальная» / «Ложное срабатывание» закрывают инцидент и пишут фидбек;
    ложное — только с кодом причины. Закрытие из OPEN подтверждает инцидент тем же действием.
41. **vision-pipeline пишет в каталог данных** (`clips/`, `frames/`, `models/engines/`) — том
    подключён на запись (в Фазе 1 был только для чтения).

## Фаза 3

42. **Образ GPU = media-base + колёса NVIDIA**, а не контейнер NGC: onnxruntime-gpu 1.31 (CUDA 13,
    cuDNN 9) и TensorRT 10.16 (`tensorrt-cu13-libs` из pypi.nvidia.com — провайдер TensorRT в
    onnxruntime 1.31 собран под `libnvinfer.so.10`, проверено по колесу; TensorRT 11 не подходит).
    Так в обоих вариантах один FFmpeg (LGPL) и один PyAV. Сборка проверяет наличие провайдеров
    TensorRT/CUDA, разрешение всех библиотек (кроме libcuda — его даёт драйвер) и лицензионный
    гейт по фактическому окружению. Лицензии NVIDIA — ревью в policy.yaml.
43. **Исполнитель моделей `auto`**: TensorRT FP16 (кэш движков по GPU/драйверу/onnxruntime), иначе
    CUDA, иначе CPU. Если GPU-провайдеры не запустились — модель работает на CPU, причина видна в
    «Состоянии системы» и в бенчмарке (не скрывается).
44. **Декодирование `auto`**: NVDEC через PyAV `HWAccel(cuda)` для камер hot path (декодируется
    каждый кадр), с откатом FFmpeg на CPU; Camera Health прочих камер декодирует I-кадры на CPU.
45. **Бенчмарк — разовым контейнером** из образа vision-pipeline (`qoima bench`) и **не
    останавливает распознавание**: если пайплайн работает, измеряется запас сверх текущей
    нагрузки (она пишется в live_load), план получается с запасом. Запуска из UI нет: у core-api
    нет доступа к Docker.
46. **Замер декодирования** — декодирование + уменьшение до миниатюры детектора движения (то, что
    hot path делает с каждым кадром), потоками в одном процессе, как в пайплайне; число потоков
    удваивается до насыщения. Для разрешений без замера ёмкость пересчитывается по пиксельной
    скорости того же кодека. Кодек без замера — предупреждение, вердикт «с ограничениями».
47. **Модель нагрузки плана**: декодирование — по родному FPS потока анализа (его не уменьшить
    понижением FPS анализа); инференс — FPS анализа × доля времени с движением + сторожевой FPS,
    поза — на каждого человека в кадре; используется не больше `capacity.utilization_target`
    ёмкости. На узле без GPU декодирование и инференс делят одну ёмкость CPU.
48. **Понижение FPS** — шагом `capacity.fps_step`, сначала у камер с наименее важным сценарием
    (`capacity.scenario_priority`), не ниже минимума сценария (SPEC.md §5.4). Не помещается и на
    минимумах — «не подходит», такой план применить нельзя.
49. **Серая зона** сужается только снижением t_high (события уходят сразу, без арбитра); t_low
    не поднимается никогда — это подавило бы тревоги. Без статистики оценок события считаются
    равномерно распределёнными в серой зоне; при ≥ `gray_stats_min_events` событиях за
    `gray_stats_days` берутся фактические оценки.
50. **VRAM**: пайплайн = контекст CUDA + замеренная память моделей + память декодеров NVDEC на
    камеру; Triton и запас — из конфига; остаток — VLM (`gpu_memory_utilization` вычисляется).
    Меньше `vlm.min_vram_gb` или остаток < `capacity.llm_min_mb` — режим без VLM. Пока VLM не
    измерен (Фаза 4), план — «без VLM», вердикт «с ограничениями».
51. **Воспроизводимость**: id плана = uuid5(sha256 всех входов), повторный расчёт по тем же
    замерам, камерам и конфигу даёт тот же план и не создаёт дубль.
52. **Применение плана** — только кнопкой администратора; пониженный FPS пишется в
    `cameras.analysis_fps` и уходит в реестр камер; на целевом FPS — NULL. При изменении камер
    или сценариев план пересчитывается для подсказки, но не применяется сам.
53. **Шаг 2 мастера** — отчёт `qoima doctor` + последний бенчмарк; ОЗУ сверяется с оценкой
    GOP-буферов (без битрейта в зондировании — 4 Мбит/с main и 0,5 Мбит/с sub).
54. **PDF** — ReportLab (BSD-3-Clause) со шрифтом DejaVu Sans (пакет fonts-dejavu-core в образе).
55. **WSL2**: `qoima up` не запускает dcgm-exporter (мониторинг DCGM в WSL недоступен) — метрики
    GPU в Prometheus отсутствуют, остальное работает.
